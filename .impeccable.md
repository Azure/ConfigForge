# ConfigForge Design Context

## Design Context

### Users

ConfigForge is a desktop workspace for IT administrators, security architects,
and baseline authors managing OSConfig security baselines across Windows,
Linux, Azure Local, and macOS author-only environments. Users work with dozens
or hundreds of settings at a time and need to inspect, compare, validate,
author, export, deploy, audit, and recover baselines without losing context.
The interface must support rapid scanning and confident high-impact actions.

### Brand Personality

**Calm, precise, trustworthy.** ConfigForge should feel like a first-party
Microsoft administration tool: technically credible, familiar to Windows and
Azure users, and restrained enough that security state—not decorative chrome—
gets attention. Copy is concise and operational. Red is reserved for confirmed
failure or non-compliance; warnings and unknown states remain neutral or amber.

### Aesthetic Direction

Use Fluent v2 / Windows 11 visual language with ConfigForge's Azure Blue
selection and action color, Segoe UI Variable typography, navy navigation,
quiet neutral surfaces, subtle dividers, and compact data-dense tables. Support
light and dark themes and coherent Windows, Linux, and macOS degradation.

The Loop design revisions establish the target information architecture:

- persistent baseline tabs that preserve work context;
- dense administrative tables instead of repeated card grids;
- explicit read-only **Code** and **Visual** viewer modes;
- editing as a separate deliberate state;
- sticky global action footers;
- stable layouts across empty, error, and loaded CIS states;
- independently scrolling work regions so navigation and global actions remain
  available.

Avoid generic dashboard-card repetition, decorative gradients, glass effects,
oversized empty states, or controls without working behavior.

### Design Principles

1. **State must be unmistakable.** Viewing versus editing, Code versus Visual,
   selected versus inactive tabs, and CIS unavailable versus loaded must be
   explicit in both text and visual treatment.
2. **Preserve context.** Open baselines remain available as tabs; content areas
   scroll independently; global actions stay anchored; switching views must not
   discard edits or reset work unexpectedly.
3. **Dense, not cluttered.** Use tables, concise metadata, purposeful status
   pills, full-value inspection, sorting, filtering, and pagination to make
   large baseline collections manageable.
4. **Every visible control works.** Disable unavailable actions with a clear
   reason; do not ship placeholder interactions, dead checkboxes, or ambiguous
   actions.
5. **Safe by default.** Destructive actions require confirmation and recovery;
   read-only views are the default; edit/deploy operations remain deliberate.
6. **Fluent and accessible.** Use FluentUI primitives, keyboard-operable
   controls, visible focus, AA contrast, reduced-motion support, forced-colors
   compatibility, and responsive adaptation rather than hidden functionality.
7. **Cross-platform coherence.** Share the same information architecture and
   tokens across Windows, Linux, and macOS while respecting flavor-specific IPC
   capability gates.
